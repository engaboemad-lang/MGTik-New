# مراجعة وإصلاح تكوين التوليد ومنطق إنشاء المستخدمين (Generation Configuration)

> **الحالة الصادقة:** الطبقة المنطقية (domain) ترجمتُها وشغّلتُ اختباراتها فعلاً (**74 اختباراً ناجحاً** في حزمة التوليد: 51 قائمة + 23 جديدة، عبر مترجم Kotlin 2.0.21 + JUnit 4.13.2 المرفقين مع Gradle). ملفات الواجهة وViewModel وCloudGateway وAppPreferences والـNavGraph **عُدِّلت ولم تُترجم** (لا Android SDK ولا شبكة هنا) وراجعتها يدوياً فقط. لا تجربة على راوتر v6/v7 حقيقي ولا على Firestore. الأمر المطلوب عند أول بناء: `./gradlew testDebugUnitTest assembleDebug`.

## 0. ملاحظة نطاق: Hotspot Server
اختيار سيرفر الهوتسبوت **أُزيل عمداً** في مرحلة سابقة (القرار: User Manager هو المرجع، لا أثر لـHotspot Users). لذلك لا يوجد اختيار سيرفر في S4 ولا في `GenerationSpec`/`GenerationCommandRequest`. لم أُعِده (يناقض القرار المعتمد). عمود Room `server` (القيمة "all") وحقل Firestore القديم باقيان كحقلين تاريخيين فقط. اختبار «تغيير السيرفر» غير منطبق لهذا السبب.

## 1. مسار التوليد: ما تُتُبِّع وما وُجد
المسار: `S4 (الحقول) → GenerationViewModel.startGeneration → StartNewOrderGenerationUseCase → GenerationRepositoryImpl (GenerationSpec في Room) → GenerationWorker → GenerationSaga → CloudGateway (PREPARE/COMMIT/BILLING) + RouterGateway (UserManSource)`.

| البند | النتيجة |
|---|---|
| وضع التوليد والسياق | تسلسلي/عشوائي يصل كما هو إلى `GenerationSpec.mode` ثم الساغا ثم وثيقة الدفعة. السياق دائماً «جملة لوكيل» (لا بيع مباشر) ويُفرض في السحابة. سليم. |
| الوكيل | إلزامي، فعّال فقط في الواجهة، ويُعاد فحصه في PREPARE (موقوف/مؤرشف يُرفض). سليم. |
| الباقة والتصنيف التجاري | **خطأ 1:** كل الباقات الفعّالة كانت تُعرض ثم تُرفض باقة SUBSCRIPTION في السحابة بعد الإرسال. **خطأ 2:** الفئة التجارية لا تُسجَّل على سجل المستخدم. |
| Hotspot Server | محذوف عمداً (البند 0). |
| إعدادات الباقة/Profile/القيود | تُحسم مرة واحدة في PREPARE عبر `ProfileSettingsReader` ← `OperationalSettingsResolver` (نفس مسار الإنشاء الفردي)، وتُقارَن مع Profile في User Manager قبل أي دفع. سليم (راجعته؛ لا تغيير). |
| الاختيارات تصل للخدمات | **خطأ 3:** اسم الباقة على الراوتر (`linkedProfileName`) كان يأتي من الواجهة (نسخة Room قد تكون قديمة بعد إعادة تسمية من جهاز آخر) ولا يُتحقق منه، واسم فارغ يُنشئ حسابات **بلا Profile** (`profileName.ifBlank { null }`). |
| تعارض إعدادات الباقة والتوليد | لا تعارض: الحدود والسرعة والصلاحية ملك الباقة ولا يرسل التوليد منها شيئاً للمستخدم. وُجد تعارض واحد في واجهة الإدخال (نمط USER_PASS_SAME القديم مع نوع كلمة مرور مستقل) فصار يُرفض. |

## 2. الأسماء والعدّادات
**السياسة المعتمدة (كما في الكود وS4):** عدّاد تسلسلي **دائم واحد لكل باقة** (`profile_defaults/{profileId}.last_assigned_sequence`) بحجز ذرّي بمعاملة Firestore؛ لا عدّاد عام. البادئة والطول لا يفصلان العدّاد (باقة واحدة = تسلسل واحد مستمر).

| البند | النتيجة |
|---|---|
| تسلسلي/عشوائي/بادئة/طول/عدد | الأسماء المنتجة تطابق الإعدادات حرفياً (بادئة + طول مولَّد بالتحديد + أبجدية النمط)؛ مثبت باختبار على 3 أنماط × 3 أطوال × 3 بادئات. |
| استمرار التسلسل | مثبت باختبار عمليتين متتاليتين (1-3 ثم 4-5) وعدّاد منفصل لكل باقة. |
| منع التكرار | داخل العملية وضد كل مستخدمي UM (مقارنة غير حساسة لحالة الأحرف)، التسلسلي يتخطى الموجود ويحرق الرقم. مثبت (9000 من 10000 مأخوذ). |
| نفاد النطاق | الحجز يُرفض **دون كتابة** (العدّاد لا يتلف). **خطأ 4:** المستخدم كان يكتشفه بعد بدء التنفيذ فقط؛ صار S4 يعرض الخطأ ويمنع التأكيد قبل أي طلب (`GenerationRules.sequenceFits`، نفس شرط السحابة، مثبت أنه مطابق). العشوائي: `ERR_GEN_KEYSPACE_EXHAUSTED` دون أثر جانبي (مثبت). |
| عدم حجز أرقام خطأً عند الفشل | الفشل قبل GENERATE (غير جاهز/باقة بلا اسم/طلب غير صالح) لا يحجز شيئاً (مثبت). إعادة المحاولة بعد فشل الراوتر **تعيد الأسماء المحفوظة نفسها ولا تحجز جديداً** (مثبت). **قرار موثَّق (لم أغيّره):** رقم حُجز ثم فشل/أُلغي التنفيذ يبقى «محروقاً» ولا يُسترجع؛ استرجاعه يتطلب حفظ المدى المحجوز في Room (تغيير مخطط) وهو أخطر على التفرّد من فجوة في الأرقام. |
| **خطأ 5 (فوترة)** | `AlreadyExists` (الاسم لحساب **ليس حسابنا**، كسباق مع مستخدم آخر) كان يُعدّ نجاحاً ⇒ كرت بكلمة مرور لا تعمل يُفوتَر. الآن يفشل الكرت برمز `ERR_GEN_USERNAME_TAKEN` (مترجم في S6) ولا يُفوتَر (مثبت). حسابنا السابق المنقطع ردّه يُعاد `Created` من `createUserClassified` أصلاً. |

## 3. كلمات المرور والتعليقات
- العشوائية (رقمية/أحرف/أرقام وأحرف/مختلطة) بالطول المحدد (4–16) والأبجدية المحددة: مثبت أن **المحفوظ = المرسل للراوتر = المرسل للسحابة**.
- «مطابقة اسم المستخدم» خيار صريح فقط؛ النمط القديم USER_PASS_SAME يعمل بلا نوع كلمة مرور، ويُرفض إن اجتمع مع نوع مستقل مختلف.
- كلمات المرور التسلسلية/الثابتة: **غير مدعومة في التصميم** (لا خيار لها) فلم أضفها.
- تفرّد كلمات المرور غير مشروط في التصميم (اسم المستخدم هو المفتاح الفريد).
- التعليق: يصل للراوتر مقصوصاً كما كتبه المختص، وفارغاً ⇒ لا يُرسل تعليق (مثبت). الربط بالمستخدم/الباقة/الوكيل/العملية يتم في سجل المستخدم السحابي (`creation_profile_id`, `owner_id`, `execution_id`, `batch_number`) **+ `category_id` الجديد**، لا في تعليق الراوتر (فلا تضارب مع تعليق المختص).

## 4–5. الباقات والواجهة
| الإصلاح | التفاصيل |
|---|---|
| إظهار الباقات المناسبة فقط | `GenerationRules.isProfileGeneratable`: فعّالة + لها اسم في UM + فئتها ليست SUBSCRIPTION. |
| إعدادات افتراضية وإعادة استخدام | `GenerationDefaults` (نقي) + حفظ محلي في `AppPreferences`: آخر إعدادات **لكل باقة**، ثم آخر إعدادات عامة، ثم المصنعية. تُطبَّق عند اختيار الباقة. تخصيصها **لا يعدّل الباقة** ولا السحابة. لا تحفظ الوكيل ولا العدد ولا التعليق. قيمة تالفة/لم تعد صالحة تُتجاهل. |
| لا بيانات قديمة عند تغيير الاختيار | عند تغيير الباقة يُعاد التسعير وتُحمَّل إعداداتها؛ اسم الباقة على الراوتر يُقرأ من السحابة وقت PREPARE. |
| معاينة قبل التنفيذ | حوار التأكيد صار يعرض: البادئة، طول الاسم، نوع كلمة المرور وطولها، ومن أول اسم إلى آخر اسم (تسلسلي) أو مثالاً (عشوائي)، مع الإجمالي التقديري. |
| منع تعارض الخيارات | التسلسلي يعطّل غير الرقمي (قائم)، ونفاد العدّاد يمنع التأكيد، وتعارض USER_PASS_SAME يُرفض. |

تسلسلي مستمر/عدّاد لكل باقة/تخطي الموجود/نفاد النطاق دون كتابة/لا حجز قبل التوليد/إعادة المحاولة بلا حجز جديد/مطابقة العشوائي للإعدادات/عدم التصادم مع موجود وعمليات سابقة/نفاد فضاء العشوائي/أنواع كلمات المرور وأطوالها/مطابقة الاسم/النمط القديم/وصول التعليق والباقة للراوتر/اسم الباقة من السحابة/باقات مختلفة/اسم مأخوذ لا يُفوتَر/5000 عشوائي (مع 100 ألف موجود) و5000 تسلسلي/مصفوفة مدخلات غير صالحة/تعارض النمط القديم/سعة العدّاد ومطابقتها للسحابة/أهلية الباقة/ترميز الإعدادات الافتراضية ورفض التالف/إعدادات لكل باقة مع احتياط عام. أُجريت **مطابقة تحقق عكسي (mutation)**: تعطيل إصلاح الاسم المأخوذ وإصلاح اسم الباقة يُفشل الاختبارين المقابلين. اختبار الدمج الذي كشف خطأي أنا (split بحد سالب) أُصلح قبل التسليم.

## 8. غير منجز / مخاطر مفتوحة (بصراحة)
1. **لم تُترجم** ملفات الواجهة/VM/Cloud/Prefs (قد يظهر خطأ ترجمة عند أول بناء، أرجّح أنه بسيط).
2. **مصالحة الاستئناف بالاسم فقط:** اسم من الدفعة موجود على الراوتر بعد انقطاع يُعدّ حسابنا دون فحص كلمة المرور (يتحقق `verifyUsers` من الوجود والباقة وعدم التعطيل فقط). الاسم يُولَّد غير موجود أصلاً فالخطر سباق نادر.
3. **كرت فشل بـUSERNAME_TAKEN** يُعاد بالاسم نفسه عند «إعادة المحاولة» فيفشل ثانية؛ يلزم قرار: استبدال الاسم (إعادة توليد للمرفوضين).
4. **الأسماء خارج الراوتر:** العشوائي يمنع التكرار مع الراوتر فقط؛ اسم مستخدم حُذف من الراوتر وما زال مطبوعاً على كرت بيد زبون قد يُعاد توليده. المنع مقابل سجل `local_users` السحابي يتطلب استعلاماً كبيراً؛ لم أنفذه.
5. فوترة `bill` تكتب العملة `"₪"` ثابتة بدل عملة الشركة/الفئة (خارج النطاق، لم أمسّه).
6. الإعدادات الافتراضية محفوظة **على الجهاز** (لا مزامنة بين الأجهزة).
7. حقل Firestore جديد: `local_users.category_id` (اختياري؛ القديم بلا الحقل، لا ترحيل ولا قواعد تتأثر).
8. لا تجربة على راوتر حقيقي: سلوك الحجز/التحقق على v6 يبقى كما في تقارير الجولات السابقة.
